# Paper-Agent 评估体系方法论

## 第一章：评估体系设计思想

### 三层金字塔评估框架

Paper-Agent 的质量评估体系采用分层金字塔设计，从组件到任务再到系统进行多维度评估：

```
           ┌──────────────┐
           │  L3 系统可靠性 │  <- 稳定性、效率、用户信号
           │  (权重 20%)   │
           ├──────────────┤
           │ L2 端到端任务  │  <- 完成率、引文有效性、LLM 裁判评分
           │  (权重 50%)   │
           ├──────────────┤
           │ L1 检索组件    │  <- nDCG、Precision、字段完整性
           │  (权重 30%)   │
           └──────────────┘
```

**各层职责：**

- **L1（检索评估）**：对论文检索服务进行组件级评估
  - 确定性指标：去重、字段完整性、多源覆盖
  - LLM 裁判指标：检索相关性、重排有序性、引文扩展质量
  - 数据集：24 条真实查询用例

- **L2（端到端评估）**：对完整的调研任务进行功能性评估
  - 确定性断言：任务完成、引文有效性、预期工具调用
  - LLM 裁判指标：综述相关性、忠实性、完整性、组织性
  - 数据集：10 条真实调研任务（holdout 防污染）

- **L3（可靠性统计）**：对系统运行日志进行统计性评估
  - 可用性指标：Turn 完成率、工具成功率、论文下载成功率
  - 效率指标：LLM 重试率、延迟分布、Token 成本
  - 用户信号：取消率、失败重试率、会话流量区分

### 混合判定思想：确定性 + LLM 裁判

评估设计的核心思想是**"确定性断言从严 + LLM 裁判从宽"**，即：

1. **确定性指标优先**
   - 能用代码逻辑直接判定的指标（如字段存在性、格式合法性、计数）优先使用
   - 结果可复现、可审计、无模型依赖

2. **LLM 裁判补充主观维度**
   - 对需要语义理解的维度（相关性、忠实性、组织性）使用 LLM 裁判
   - 采用 1-5 分制，模型统一配置（见 config/model.json 的 eval_judge 档位）
   - 不一票否决：裁判评分仅作为聚合指标之一，占权重不超过 20%

3. **为什么裁判不一票否决**
   - LLM 评估本身存在 self-preference 风险（同族模型倾向互相评分高）
   - 单一模型的标准可能过于严格或宽松，需要多指标组合判定
   - 确定性指标提供客观基准，防止评分虚高

## 第二章：快速开始

### 环境要求

- Python 3.10+
- Conda 虚拟环境：`paper-agentic`（**uv 不可用**）
- 依赖：見 eval/requirements.txt（如有）

### 关键准备工作

**L2 端到端评估需要后端服务**。在运行 L2 前，需在另一个终端启动后端：

```bash
# 启动后端（无 reload 热加载，便于评估流量统计）
conda run -n paper-agentic python src/api/main.py --reload=false --host 127.0.0.1 --port 8000
```

### 三条最常用命令

#### 1. 零成本可靠性统计（仅 L3）
快速了解系统运行状态，无任何 API 或 LLM 调用成本。

```bash
conda run -n paper-agentic python eval/run_all.py --skip-l1 --skip-l2
```

**预期输出：**
- 评估完成 < 1 分钟
- 输出总分（100% 来自 L3）
- 成本：¥0.00

#### 2. 快速回归测试（跳过 LLM 裁判）
检查组件和任务功能是否正常，用确定性指标判定，无裁判调用。

```bash
conda run -n paper-agentic python eval/run_all.py --skip-judge
```

**预期输出：**
- L1 用例数、检索质量指标（nDCG 等为未测）
- L2 用例完成率、引文有效率
- L3 可靠性统计
- 成本：¥0.00

#### 3. 全量评估（包含 LLM 裁判）
完整评估系统质量。**需提前启动后端**。

```bash
conda run -n paper-agentic python eval/run_all.py
```

**预期输出：**
- L1、L2、L3 全部运行（含 LLM 裁判）
- 总分=0.3×L1 + 0.5×L2 + 0.2×L3
- 成本：¥1~5（取决于数据集规模、模型价格）

## 第三章：各 Runner 用法详解

### run_all.py（聚合入口）

**功能：** 依次运行三层评估，聚合总分，生成趋势对比报告

**基本用法：**
```bash
conda run -n paper-agentic python eval/run_all.py [选项]
```

**常用选项：**

| 选项 | 说明 | 示例 |
|------|------|------|
| `--skip-l1` | 跳过 L1 检索评估 | `--skip-l1 --skip-l2` 仅跑 L3 |
| `--skip-l2` | 跳过 L2 端到端评估 | - |
| `--skip-l3` | 跳过 L3 可靠性统计 | - |
| `--skip-judge` | 跳过 LLM 裁判（仅确定性指标） | 快速回归使用 |
| `--only-l1 r01,r02` | L1 仅运行指定用例（逗号分隔） | 单个用例调试 |
| `--only-l2 e01` | L2 仅运行指定用例 | - |
| `--replay-l1 DIR` | L1 重放历史数据（指定原 raw/ 目录） | 复现历史结果 |
| `--include-holdout` | L2 包含 holdout 测试用例 | 最终验证前使用 |
| `--calibration` | 运行校准集评估 | 校准 LLM 裁判 |
| `--base-url URL` | L2 后端地址（默认 http://127.0.0.1:8000） | 连接远程后端 |
| `--out-dir DIR` | 输出目录（默认 eval/reports/{时间戳}） | 指定输出位置 |

**输出文件：**
- `report.json`：机读版报告（schema 冻结）
- `report.md`：人读版报告
- `retrieval.json` / `e2e.json` / `reliability.json`：各层原始数据（run_all 透传）

## 第四章：报告怎么读

### 总分公式与归一规则

**基础公式：**
```
总分 = 0.3 × L1 + 0.5 × L2 + 0.2 × L3
```

**权重归一规则**（某层被跳过时）：
- 若 L1 被跳过，则 L2 和 L3 的权重按比例增大
- 例：`--skip-l1` 时，总分 = 0.625 × L2 + 0.375 × L3
- 报告显著标注"本次总分不含 L1 层"

**单层得分公式：**
```
层分 = (该层所有参与计分的指标的分数) 的算术平均
```

### 指标定义表

#### L1 检索评估指标

| 指标 | 含义 | 单位 | 阈值 | 方向 | 数据来源 |
|------|------|------|------|------|---------|
| **nDCG@10** | 检索排序质量（0~1） | 分数 | ≥0.75 | 越高越好 | 裁判评分 |
| **Precision@10** | 检索相关性（0~1） | 比率 | ≥0.7 | 越高越好 | 裁判评分 |
| **Golden Recall** | 金标论文召回率（0~1） | 比率 | ≥0.6 | 越高越好 | 裁判评分 |
| **Abstract 完整性** | 论文摘要字段完整率（0~1） | 比率 | ≥0.9 | 越高越好 | 确定性 |
| **字段错误率** | 查询结果无错误的比率（0~1） | 比率 | ≥0.8 | 越高越好 | 确定性 |
| **去重违规** | 重复论文计数 | 计数 | =0 | 违规→0分 | 确定性 |
| **多源覆盖率** | top-10 中来自≥2个源的论文比率（0~1） | 比率 | 无 | 趋势指标 | 确定性 |
| **搜索延迟 P95** | 95 分位数（秒） | 秒 | ≤15s | 越低越好 | 确定性 |

#### L2 端到端评估指标

| 指标 | 含义 | 单位 | 阈值 | 方向 | 数据来源 |
|------|------|------|------|------|---------|
| **完成率** | 任务完成的用例占比（0~1） | 比率 | ≥0.9 | 越高越好 | 确定性 |
| **引文有效率** | 最终答案引文可对应回源（0~1） | 比率 | ≥1.0 | 越高越好 | 确定性 |
| **断言通过率** | 预期的功能断言通过的比率（0~1） | 比率 | 无 | 趋势指标 | 确定性 |
| **相关性评分** | 综述相关性（1~5） | 分数 | ≥3.5 | 越高越好 | 裁判评分 |
| **忠实性评分** | 论断忠实于论文（1~5） | 分数 | ≥3.5 | 越高越好 | 裁判评分 |
| **完整性评分** | 主要观点完整覆盖（1~5） | 分数 | ≥3.5 | 越高越好 | 裁判评分 |
| **组织性评分** | 论证逻辑清晰（1~5） | 分数 | ≥3 | 越高越好 | 裁判评分 |
| **首字节延迟（TTFT）** | 首块输出延迟（秒） | 秒 | 无 | 趋势指标 | 确定性 |

#### L3 可靠性指标

| 指标 | 含义 | 单位 | 阈值 | 方向 | 数据来源 |
|------|------|------|------|------|---------|
| **Turn 完成率** | 完成的 Turn 占比（0~1） | 比率 | ≥0.9 | 越高越好 | 事件流 |
| **工具成功率** | 工具调用成功占比（0~1），**按步骤去重**（见下方口径说明） | 比率 | ≥0.95 | 越高越好 | 事件流 |
| **LLM 重试率** | 失败重试的 LLM 调用占比（0~1） | 比率 | ≤0.1 | 越低越好 | 日志 |
| **论文下载成功率** | 真正发起过下载/精读的论文中，全文成功落地的占比（0~1），**尝试口径** | 比率 | ≥0.9 | 越高越好 | 事件流 + 工作区 |
| **Abstract Fallback 率** | 真正发起过精读的论文中，降级用摘要的占比（0~1），**尝试口径** | 比率 | ≤0.2 | 越低越好 | 事件流 + 工作区 |
| **检索放宽率** | 触发放宽搜索的 Turn 占比（0~1） | 比率 | ≤0.3 | 越低越好 | 事件流 |
| **评估覆盖率** | 有工作区的会话中，至少评估过一篇论文的会话占比（0~1），**会话级** | 比率 | ≥0.8 | 越高越好 | 工作区 |
| **取消率** | 用户主动取消的 Turn 占比（0~1） | 比率 | ≤0.05 | 越低越好 | 事件流 |

### 口径说明（2026-09-10 修订）

**为什么要改**：最初实现用「工作区里累积的全部论文条目」当分母，实测 244 篇里 242 篇是用户从没要求下载的检索结果，于是论文下载成功率被算成 0.4%（1/244），而阈值是 0.9——在这个口径下**数学上永远不可能达标**，指标失去意义。同时工具调用计数把同一步骤反复上报的进度事件当成多次调用，`deep_read_paper` 被算成 64 次（真实只有 2 次），所有失败率的分母都跟着失真。

**现在的规则**：

1. **尝试口径**（下载成功率 / Abstract Fallback 率）
   - 分母 = 从事件流里真正发起过 `download_paper` 或 `deep_read_paper` 的论文数（`(会话, 论文编号)` 去重）。精读内部也会去拿全文，因此精读同样计入下载尝试。
   - 分子 = 这些论文里全文真正落到本地缓存的篇数 / 降级为摘要的篇数。
   - 历史基线：下载 1/2 = 50.0%，Fallback 1/2 = 50.0%。

2. **按步骤去重**（工具调用次数）
   - 一个步骤由同一轮对话内的 `event_key` 唯一标识；一个耗时长的工具会反复上报 `status='running'` 的进度事件（实测一次 6 分 43 秒的精读上报了 58 条），**只有首次计一次调用**。
   - 修复后 `deep_read_paper` 64 → 2、`generate_review` 25 → 1；`search_papers`（32）和 `expand_by_citations`（7）本就是真实调用数，不变。

3. **会话级**（评估覆盖率）
   - 分母 = 有 `workspace/papers.json` 的会话数；分子 = 其中至少有一篇论文被评估过的会话数。
   - 历史基线：5/9 = 55.6%。

**读数纪律**：小样本指标必须连分子/分母一起看。JSON 与 Markdown 报告已同时输出原始分子分母（如 `download_succeeded` / `download_attempted`），终端摘要也会带上样本量——单独一个「50%」在 n=2 时不构成结论。

**趋势连续性**：本次口径变更（2026-09-10）之后，`run_all.py` 的「趋势对比」会把新口径结果与旧口径的历史报告相比，得出**虚高的提升**（实测 L3 由 75.5 跳到 84.4，其中相当一部分来自口径修正而非真实改进）。跨这次变更的趋势数字不可直接采信；等下一次全量评估跑完，基线才恢复可比。

### 符号含义

| 符号 | 含义 | 说明 |
|------|------|------|
| **⚠️** | 警告 | 该指标低于/高于阈值，系统可能存在风险 |
| **↑** | 上升趋势 | 当前值比上次运行 >0.5% 提升 |
| **↓** | 下降趋势 | 当前值比上次运行 <-0.5% 下降 |
| **→** | 平稳 | 变化 <0.5%，无显著变化 |
| **未测** | 不可用 | 因 --skip-judge 或其他原因缺数据 |
| **N/A** | 不适用 | 无历史对比或指标不存在 |

### 如何理解各部分

1. **总览部分**
   - 总分是综合各层的加权平均
   - 趋势显示与上次运行的对比（首次运行显示"无历史对比"）
   - 报告路径便于审计和归档

2. **分层详情**
   - 每层的聚合指标表展示该层的核心质量指标
   - 用例详情行展示各用例的状态（完成/失败/跳过）
   - 若某层被跳过或失败，相应行显示"⊘"或 failed 标记

3. **附录**
   - 校准结果（若运行了 --calibration）
   - 成本明细（L1、L2、L3 各自的成本）
   - 数据质量备注（缺失数据、已知偏差说明）

## 第五章：LLM 裁判可信度

### 校准集标注指南

LLM 裁判的可信度关键取决于校准集的标注质量。校准集位于 `eval/datasets/judge_calibration.json`。

**标注格式示例：**
```json
{
  "case_id": "calibration_001",
  "prompt": "评估这篇综述对深度学习基础的介绍是否完整...",
  "model_output": "...",
  "gold_label": 2,
  "instructions": "0=完全不完整，1=基本覆盖，2=全面且深入"
}
```

**标注流程：**
1. 由领域专家独立标注（目标 30~50 条样本）
2. 按 instructions 明确定义各档锚点（相关性裁判现在是 0~4 五档）
3. 运行 `python eval/run_all.py --calibration` 评估标注一致性

### 一致率、Spearman 相关系数、混淆矩阵解读

运行 `--calibration` 后，报告附录会显示：

**一致率（Accuracy）**
- 含义：裁判与金标标注完全一致的样本占比
- 目标：≥85%（达到即可用于评估）
- 若 <85%，显示警告"裁判可信度不足，本次 judge 分仅供参考"

**Spearman 相关系数**
- 含义：裁判分数与金标分数的排序相关性（-1~1）
- 目标：≥0.8（强相关）
- <0.6 表示存在系统性偏差，需调查模型输入设置

**混淆矩阵**（相关性裁判为 0~4 五档，矩阵随之是 5×5）
```
            | 裁判=0 | 裁判=1 | 裁判=2 | 裁判=3 | 裁判=4 |
------------|--------|--------|--------|--------|--------|
金标=0      |   a    |   b    |   c    |   d    |   e    |
金标=1      |   f    |   g    |   h    |   i    |   j    |
金标=2      |   k    |   l    |   m    |   n    |   o    |
金标=3      |   p    |   q    |   r    |   s    |   t    |
金标=4      |   u    |   v    |   w    |   x    |   y    |
```
- 对角线元素越大越好（一致判定）
- 若某列或某行明显偏高（如 e 很大），说明裁判倾向于某个标签，需调查

### 校准工作流

1. 初次标注 30~50 条，运行 `--calibration` 检查一致率
2. 若一致率 <85%，分析混淆矩阵：
   - 若裁判倾向给高分：可能是模型 temperature 过高，尝试 temperature=0.0
   - 若裁判倾向给低分：检查 prompt 是否过于严苛
3. 调整 prompt 或模型参数后，补充标注 10~20 条，再次运行
4. 迭代直到一致率 ≥85%

### 使用历史校准结果

校准完成后，下次评估可跳过 `--calibration`，直接用 `run_all.py` 进行评估。校准结果 cached 在 `eval/datasets/judge_calibration.json` 中，无需重复标注。

## 第六章：已知偏差与注意事项

### 1. LLM 自我偏好风险（Self-Preference Bias）

**现象：** 用同一系列的模型互相评分时，往往给对方较高评分

**缘由：** 模型倾向于认可与自己风格相近的输出

**对策：**
- 若需要更客观的评估，可在 `config/model.json` 的 `eval_judge` 档位切换为异构模型（如 Claude 评估 Deepseek 输出）
- 或在校准集中混入多模型的输出，进行混合标注

### 2. 线上 API 价格/接口漂移风险

**现象：** 如果评估依赖的外部 API（如 ArXiv、Semantic Scholar、OpenAlex）发生变化，搜索结果可能改变

**缘由：** 这些 API 不保证历史结果的完全再现

**对策：**
- 趋势对比时应关注**相对变化**而非绝对值
- 若某次评估后 API 显著变化，在报告中记录该事件
- 可用 `--replay` 重放历史原始数据进行对标

### 3. 工具级耗时无法单独测量（P4 待埋点）

**现象：** L3 中工具执行的 p50/p95 延迟为 0

**缘由：** 事件流中各工具的 created_at 和 completed_at 时间戳精度有限（同值）

**对策：**
- 目前参考 **Turn 级耐时** 作为系统响应性指标
- P4 待增加微秒级时间戳埋点，方可精确测工具耗时

### 4. 成本估算是价目表维护的估算值

**现象：** 报告中"成本估算"可能与实际 API 账单不符

**缘由：** `eval/config.py` 中的 `PRICE_TABLE_CNY_PER_M_TOKENS` 是占位价格

**对策：**
- 定期（如每季度）更新 `PRICE_TABLE_CNY_PER_M_TOKENS` 为官方最新价目
- 可用此表对 Token 用量进行估算，对标真实成本

### 5. Holdout 测试集防污染

**现象：** 若评估过程中使用了 holdout 用例，会污染最终验证集

**用法：**
- 日常评估：`python eval/run_all.py --skip-l2` 或 `--only-l2 e01,e02,...` 仅用主集
- 最终验收前：`python eval/run_all.py --include-holdout` 包含 holdout，作为 final check

### 6. 评估流量 vs 真实流量分离

**原理：** L3 统计自动以会话 title 前缀 `eval_` 区分：
- `eval_...` 前缀的会话 → 评估流量（虽包含真实用户转发，但由脚本驱动）
- 其他会话 → 真实用户流量

**含义：** L3 中的"Turn 完成率""工具成功率"等指标仅统计真实流量（或按需包含评估流量）

**在报告中查看：** `traffic_split.real` 和 `traffic_split.eval` 分别展示两类流量的统计

## 附录：常见问题排查

### Q: 运行 `run_all.py` 出现 "ModuleNotFoundError: No module named 'src'"

**A:** 确保使用正确的 conda 环境和工作目录：
```bash
cd D:\工作区\Paper-Agent-main
conda run -n paper-agentic python eval/run_all.py ...
```

### Q: L2 运行报 "Connection refused" 或后端超时

**A:** 检查后端是否启动：
```bash
# 另一个终端启动后端（保持运行）
conda run -n paper-agentic python src/api/main.py --reload=false --host 127.0.0.1 --port 8000

# 或指定远程 URL
python eval/run_all.py --base-url http://your-server:8000
```

### Q: 裁判评分全是 None 或 "未测"

**A:** 检查是否使用了 `--skip-judge`，或者裁判初始化失败。查看子进程的 stderr 输出。

### Q: 报告总分为 0 或 NaN

**A:** 可能所有层都被跳过或失败。运行至少一层（如 `--skip-l1 --skip-l2` 仅跑 L3）。

### Q: 对比两次运行结果，为什么都是 L3 但分数不同？

**A:** L3 统计是实时的，包括最新生成的评估会话。若两次运行间有新会话，L3 数据会更新。这是预期行为，报告中会注明"运行中评估会话计入 eval_ 流量口径"。
