## 一句话总评

这篇文档的骨架（四层 + 决策卡片 + 失败故事）是好的，但"模型调用失败"这条最重要的收场路径讲错了——文档说重试都失败会补 `turn_end(failed)`，实际走的是成功收尾、会话标成 `completed`，新人照着这篇去查日志会查错方向。

## 一、必须保留的东西

改写时不许丢掉下面这些做法，它们是这篇文档真正的价值：

- **开头「读完这一篇，你能回答」的 5 个问题，和小结的 5 条一一对应**（L5-11 ↔ L314-320）。首尾呼应，读完能自查。这是整套文档统一的好格式，保留。
- **第 0 节的四层 mermaid 图**（L23-29）和"从上往下走，每一层挡掉一类问题"的讲法（L21）。一句话把全篇结构交代清楚，是新人进入本篇的锚点。
- **决策卡片的三段式**（要解决的问题 / 考虑过的做法 / 最终选择 / 代价）。尤其每张卡片末尾的"代价是什么"——工程文档里很少有人肯写代价，这里写了，保留。
- **决策 5 的那张对照表**（L87-94）。"拿不到全文可以降级，读不到正文不许假装读过"是全篇最值钱的一句话，也是这个项目可用性设计的分界线。保留原表和原话。
- **决策 2「并发名额只在真正发请求时占用」的讲法**（L49-57），特别"睡眠放在信号量外面"这个具体到实现的点。这是新人读代码时最容易看漏的地方。

- **第 2.2 节下载出口的 1~5 编号清单**（L186-193）。每条一个状态名 + 一句中文原因，是新人照着查 `download.py` 的最短入口，写法要保留（否定句要改，见第二部分）。
- **第 3 节「场景 / 策略」对照表**（L201-212）。把"哪种失败怎么处理"集中成一张表，比散在正文里好得多。
- **第 4.1 节结尾的顺序解释**（L226）："顺序反过来的话，任务结束太快，前端来不及看到中间状态"。把"为什么是这个顺序"讲出来了，保留。
- **第 7 节的失败故事**（L286-312）：一张 mermaid 图 + 7 步展开，把四层串成一条真实路径。这是全篇对新人最友好的一节（建议提前，见第六部分）。
- **第 6 节末尾的坦白**（L282）："这些不是加密措施"，说明这些措施真正减少的是"整轮失败"。不夸大，保留。
- **行号引用格式 `83:84:src/api/app.py`**（L248-251）。和 README 约定的 `起始行:结束行:文件路径` 一致，保留并继续用。

## 三、与源码不符的地方

### 1. `L168` 文档说：「再由 run 服务补一个 `turn_end(failed)`。」

源码实际：主 Agent 在模型调用失败时**不是抛异常**，而是发一条固定话术的助手消息后 `return`（`src/agents/research/agent.py:283-296`）。`_run_in_background` 只在 handler 正常返回后判断是否收到取消请求，没收到就调 `_finalize_success`（`src/services/session_runs.py:401-411`），`_finalize_success` 发出的 `turn_end` 里 `status` 是 `completed`，会话也写成 `completed`（`src/services/session_runs.py:438-466`）。真正发 `turn_end(failed)` 的只有 handler 抛异常那条路（`src/services/session_runs.py:526-570`）。
建议改成：「再由 run 服务补发 `turn_end`。注意这条路径是正常返回，所以收尾状态是 `completed`，会话不会被标成 `failed`。」

### 2. `L316` 小结第 1 条文档说：「重试都失败就用固定话术收尾，run 补一个 `turn_end(failed)`。」

同第 1 条，证据同上（`src/agents/research/agent.py:283-296`、`src/services/session_runs.py:410`、`src/services/session_runs.py:459`）。
建议改成：「重试都失败就用固定话术收尾，run 照常补发 `turn_end`（状态是 `completed`）。」

### 3. `L226` 文档说：「先发 SSE `cancel_requested`，文案是「正在保存当前进度」。」
