# doc/ 改写总纲（跨篇统一口径，改写时以此为准）

这份总纲由主控写定。改写每一篇之前先读它。总纲与某一篇的诊断文件冲突时，以总纲为准；
总纲没覆盖的，以该篇诊断文件 + 两份 verify 文件为准。

把这套文档改到「一个从没接触过本项目的人，能按顺序读下去并尽快上手」。
保留原有讲法（短句、第二人称「你」、打比方、每节都写「代价是……」），不要换腔调。

## 三、统一后的章节结构（五篇分篇一致）
1. 文首 `# 标题`
2. `## 读完这一篇，你能回答` —— 5 个问题
3. `## 0. 先看全局` —— 只讲「有哪些东西、它们什么关系」，配图。**所有会用到的名词在这里先给一句话解释**
4. `## 1.` `## 2.` …… 正文，讲机制本身。**先讲是什么、怎么走，再讲为什么**
5. `## 设计理念：为什么是这个形状` —— 原来的决策卡片整节移到这里，编号接正文
6. `## 小结`
7. `## 延伸阅读`

### 关于「设计理念」后移（本次最重要的结构改动）
现状是决策卡片排在正文之前，新人还不认识工具卡、工作区、档位，就先读十几条取舍，
读不下去。本次一律改为：
- 正文各节里，凡涉及某个取舍，写一句指路：「这个选择的来龙去脉见第 N 节决策 M。」
- 决策卡片整节移到正文之后、小结之前，编号顺延。
- 决策卡片本身保持「要解决的问题 / 考虑过的做法 / 最终选择 / 代价是……」四段式，一个字都不要丢。
- 决策内部若大段展开了正文已讲过的机制，压成一句结论 + 指回正文小节。

### 关于「动手改一处」（只给 01 和 03 加，各不超过 12 行）
01 结尾加：想给主 Agent 加一个工具 / 改一句系统提示词，分别动哪几个文件。
03 结尾加：新增一个工具要走哪几个文件、改一个工具的入参要同步改哪里。

## 五、语言规范（硬要求）
1. 句子：以句号/问号/叹号/分号切分后，单个句子构件不超过 40 个汉字。**30 个以上一律拆**。
   逗号连成的长句，总长不超过 100 字。
2. 被动改主动（「被切坏」→「切坏」/「配对会断」）。
3. 否定句能改肯定就改；双重否定一律改。
4. 的/地/得用对：形容词+的+名词；副词+地+动词；动词+得+副词。
5. 代词（其/该/此/这）必须只有一个意思。
6. 名词前不要堆长定语，拆成后置短句。
7. 生造比喻动词替换（这是本套文档的主要违规）：
   - 收口 → 统一处理 / 归并
   - 抹平、吃掉 → 消除差异 / 统一处理
   - 串台 → 互相干扰
   - 兜住 → 保住 / 处理
   - 盖掉 → 覆盖
   - 口径 → 判断条件
   **保留不动**：落库、落盘、装箱、档位、片段、快照、精读、工作区、工具卡、检查点、降级、封顶、退避。
8. 英文首现给中文标注。必补的 9 处：token、DOI、venue（→发表刊物）、handler（→处理函数）、
   connector（→数据源连接器）、RRF、WAL、URI、SHA-256。另外正文首次出现时补：LLM、SSE、JSON、
   PDF、SQLite、API、HTTP、SDK、ReAct、ContextVar、map-reduce、LangGraph、asyncio、httpx。
   注意只在**整套文档的首次出现处**补，不要在每一篇都补一遍（阅读顺序：arch/README → 01 → 02 → 03 → 04 → 05）。
9. 中文里用「……」不用 "..."；半角标点只出现在代码或引用格式里，且要用反引号包起来。
10. 专有名词大小写：HTTP/HTTPS 大写（`04` 里「http 和 https」要改）。
