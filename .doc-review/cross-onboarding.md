> 审查人身份：会写 Python，懂 Web 后端，没读过本仓库一行代码。
> 阅读顺序：doc/arch/README.md → 01 → 02 → 03 → 04 → doc/LLM-README.md。
> 辅助材料：根目录 README.md、根目录 使用说明.md、源码抽查。
> 审查日期：2026-09-29。

## 结论摘要

这套文档的机制讲解质量很高。术语表、每篇开头的「读完这一篇，你能回答」、决策段的四段式（问题 / 备选 / 选择 / 代价），都对新人有用。句子也干净：全 doc 正文最长的句子构件是 27 个字，没有一句达到 30 字，全部符合中文技术写作规范的长度要求。

真正的短板只有两处：

1. **没有入口。** doc/ 里没有一个字讲「怎么装、怎么配模型、怎么启动」。新人读完这套文档，仍然不知道怎么把项目跑起来。
2. **顺序反了。** 01 和 04 都假设读者已经懂「档位」和「模型配置」。配置的完整说明却在最后一篇（LLM-README）。

## 一、读完 doc/arch/README.md，新人能说清「项目是什么、分成哪几块」吗

### 能说清的部分（做得好，保留）

- 「Paper-Agent 是一个论文调研工具」这句话在第 3 行就出现。接着一句话讲完主流程：输入主题 → 检索论文 → 逐篇阅读 → 写出综述。这就是新人最需要的「一句话说清产品」。
- 「全局一张图」给了两层结构：横向六层（前端 / 接口 / 服务 / Agent / 工具 / 数据），纵向一次运行的全链路。两张图配合，能回答「分成哪几块」。
- 「代码放在哪」的目录树按包分组。每一行都带一句职责说明，可以单独当索引用。
- 「改一个功能之前，先看下面几行」把「加工具 / 加接口 / 改提示词 / 改界面」分别指到具体目录。这是整篇最好用的部分。

### 含糊的地方（建议补）

**1. 没说运行形态。**

第 5 行只写「前端是网页，后端是 FastAPI 服务」。新人不知道这是本机单机应用，也不知道它只有两个端口。

- 位置：doc/arch/README.md 第 5 行之后。
- 改法：补一句「这是本机单机应用。后端默认监听 `127.0.0.1:8000`，前端开发服务在 `127.0.0.1:5173`。数据全部存在本机 `data/` 下。」

**2. 没说「产物」是什么。**

「产物」全 doc 出现 16 次，术语表里没有。新人在第 124 行第一次遇到它（「产物的正文写在会话目录的文件里」），只能靠猜。

- 位置：doc/arch/README.md 术语表。
- 改法：补一行。见第三节的现成文案。

**3. 没提「上传自己的 PDF」。**

这是产品的一个重要入口。它写在 使用说明.md 第四节和根目录 README 里，doc/ 完全没有。新人看完 doc/，会以为系统只能检索外部论文。

- 位置：doc/arch/README.md 第 122 行「还有几条约定」。
- 改法：补一行「用户也能把本机 PDF 拖进工作区。上传件和检索到的论文走同一条路。原文存在 `data/paper_cache`，删这个目录会连带删掉原文。」

**4. 入口文件的身份含糊。**

这套文档的入口叫 `doc/arch/README.md`，但它统管五篇。其中 `doc/LLM-README.md` 在 `arch/` 目录之外。新人浏览 `doc/` 文件夹，会看到 `arch/README.md` 和 `LLM-README.md` 两个入口，容易以为前者只管 arch 四篇。

- 改法（二选一）：
  - 只改现状：在标题「# Paper-Agent 源码讲解文档」下面加一行「本文档是 `doc/` 的总入口，同时讲 `doc/arch/` 四篇和 `doc/LLM-README.md`。」
  - 新增 `doc/README.md`：内容 5 行，指向 `arch/README.md`，并写明它是唯一入口。推荐这一条，长期更清楚。

**5. 没有文档版本。**

第 9 行只说「以后改代码，行号可能漂移」，但没有写这几篇对应哪个提交或日期。新人无法判断文档是否过期。

- 位置：doc/arch/README.md 第 9 行。
- 改法：补一句「本文档核对过 2026-09-29 的 main 分支。」

## 四、缺失的入口：doc/ 该不该教人怎么跑起来

### 现状（已核实）

doc/ 下 6 个文件全部是源码机制讲解。在 `doc/` 里检索「uv sync」「npm run」「start.bat」「main.py」「快速开始」「使用说明」，**零命中**。

安装、配置、启动三件事写在两处：

- 根目录 `README.md` 的「🚀 快速开始」：开发双服务模式、单端口模式、打包分发三种形态。
- 根目录 `使用说明.md`：面向拿到压缩包的普通使用者。

### 判断：放指针，不放全文

三条理由：

1. **避免第四份副本。** 同一套步骤已经有三种形态。doc/ 再抄一遍，就有了第四份要同步的文本。
2. **改动频率不同。** 启动方式跟着 `start.bat`、`scripts/launch.py`、`scripts/package.py` 变。doc/ 讲的是代码机制，改动频率低得多。
3. **新人要的是「去哪找」。** 文档不必重复别人已经写对的步骤。

### 具体补法（三处）

**补法一**：doc/arch/README.md 第 5 行之后（「一共五篇」那段之前）插入一小节。

```markdown
## 先把项目跑起来

这套文档只讲代码怎么搭起来，不讲怎么安装和启动。

- 想在自己的电脑上跑起来开发：看根目录《README.md》的「🚀 快速开始」。
- 拿到了一个压缩包，想双击就用：看根目录《使用说明.md》。
- 这两份讲的是「怎么用」，本文档讲的是「为什么这么写」。
```

**补法二**：同一篇第 122 行「还有几条约定」里补三条「读代码前的最小配置事实」。

01 和 04 都假设读者懂「档位」。这个知识的完整说明在最后一篇（LLM-README 的「config.py」一节）。把最小三条前置：

```markdown
- 模型配置分两个文件：`config/model.json` 放连接与密钥，`config/system.yaml` 放系统默认值。
- 内置档位只有 `default_agent`。它是唯一必需的档位，缺了它系统起不来。
- 主 Agent 用 `research_agent` 档位。这个档位没配时，自动回退 `default_agent`。
  完整说明见 [LLM 适配层](../LLM-README.md) 的「config.py」一节。
```

**补法三**：指向根目录 README 时，同时说明有一处不一致。

根目录 README.md 的架构图写「主对话共注册 10 个工具」，漏了 `get_history`。本套文档写的是 11 个，与源码一致（`src/agents/research/tools.py:523-533` 有 11 行 `registry.register`）。建议在补法一的指针下加一句「工具数量以本套文档的 11 个为准」。

## 七、跨篇一致性核对

### 一致性问题 1：token 用量是「累加」还是「覆盖」（涉及简历红线）

三处写「累加」，另一处写「覆盖」，同一套文档自相矛盾。

| 位置 | 原文 |
| --- | --- |
| doc/arch/README.md:200 | 「它还要累加 token 用量」 |
| doc/arch/01-agent-orchestration.md:405 | 「用量也就累加到对应的那张工具卡上」 |
| doc/arch/04-availability.md:265 | 「子 Agent 的用量累加到所属工具卡」 |
| doc/arch/01-agent-orchestration.md:718 | 「用量只在显式传入时覆盖」 |

事实是：**卡片上的用量是覆盖**，不是累加。真正的累加发生在上报之前——一次节点内的多次模型调用先攒成一个总数，再上报一次。

改法（三处）：

1. arch/README.md:200，「累加 token 用量」改成「更新 token 用量」。
2. 01:405，「累加到对应的那张工具卡上」改成「覆盖到对应的那张工具卡上」。
3. 04:265，改成「每张工具卡带真实的 `input_tokens` / `output_tokens`。这些数字是覆盖式更新，只在模型回调提供用量时写入。子 Agent 上报之前，先把一次节点内多次调用的用量攒成一个总数。」

### 一致性问题 2：`llm_json.py` 的表述

- 位置：doc/arch/README.md 第 101 行。
- 原文：「`llm_json.py            模型输出 JSON 的统一解析入口`」。
- 事实：`analyse.py` 已用 `parse_llm_json`，但自带外层重试。`outline.py` 和 `writing.py` 仍是手写解析。
- 改法：改成「精读、问答、插图解读、综述分析共用这一份解析；大纲和逐节写作仍各自解析」。
- 说明：这一条在此前的 `.doc-review/arch-readme.verify-edge.md` 第 1 条已经确认，此处只做跨篇登记。

### 一致性问题 3：`get_chunk_by_embed` 提到「以后接上向量库」

- 位置：03 §2 表格最后一行，以及 03 决策 11 的结尾。
- 原文：「以后接上向量库时，只要换掉函数内部实现。」
- 问题：这句话容易被读成「项目规划了向量库」。本项目没有跨会话的语义向量召回，被否决的方案才是「向量库」。这句话在面试追问下会变成风险。
- 改法：改成「这是给未来留的接口占位。当前不接任何检索实现，调用它会返回『暂未实现』。」去掉「向量库」三个字。

### 一致性问题 4：工具数量

- 根目录 README.md 写 10 个，漏了 `get_history`。这不算 doc/ 的错，但 doc/ 指向根 README 时要提醒一句。
