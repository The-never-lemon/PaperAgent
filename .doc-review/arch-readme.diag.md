# doc/arch/README.md 诊断

## 一句话总评

这篇文档的**骨架和讲法是合格的**（三层一图、七个"要解决的问题 / 考虑过的做法 / 最终选择"、二十条术语表），真正的问题有两类：一是**三处关键表述踩了简历红线**（"统一 JSON 解析入口""token 用量累加"）或**指向了错误的文件**（`src/config/baseAgent.md` 其实是外项目的文档）；二是**为了通俗而生造的比喻动词太密**（抹平、认领、盖掉、折叠、闸门、剥、撑到、瘦身、一节一笔），新人读完记得住比喻、记不住机制。

## 一、必须保留的东西

改写时以下结构、讲法、图一律不许丢。

### 1. 开篇的五问（L11-L17）

```
读完这一篇，你能回答五个问题：
1. Paper-Agent 是做什么的？用户输入什么、拿到什么？
...
```

"先给读者一个可验收的目标，再开始讲"这个做法要保留。它让新人知道读到什么程度算读完。

### 2. 术语表（L19-L39）

二十个词集中在开篇一次性定义，是这篇文档最有价值的部分。尤其是这几条，写得比项目里任何注释都清楚：

- `L23` 「主 Agent 直接和用户对话，自己决定下一步做什么。子 Agent 干精读、追问、综述这三件事，由主 Agent 当工具调起来」
- `L24` 「模型不直接干活。它只说调哪个工具、参数是什么，真正执行的是代码」——一句话讲清了 function calling
- `L27` 「用户发一条消息，到系统回复结束，中间的全部过程」——把"一次运行"的边界划死了
- `L31` 「停掉后从最后一个写完的步骤接着做。正在写的那一节要重做」——检查点粒度写得比 04 篇还准

**保留整张表**，只做措辞微调（见第二节），不要拆散。

### 3. 用词的三条例外（L41-L45）

> 逐字引用源码、日志或提示词原文时，不受上表的用词约束。
> 「快照」在本套文档里指模型配置快照（`ProviderSnapshot`），和检查点是两回事。
> 被项目否决的方案，文中仍按当时的叫法称呼，比如「向量库」。

这三条把"术语表冲突时以谁为准""快照和检查点别混""被否掉的方案怎么写"三件事一次说清，是整套文档的用词宪法。

### 4. 文档索引表（L47-L53）

四篇分篇 + LLM 篇，每行给"讲什么 / 核心文件"，且**核心文件是真的**（逐条核过：`session_runs.py`、`research/agent.py`、`review/pipeline.py`、`common/context_budget.py`、`services/paper_memory.py`、`research/tools.py`、`common/tool_registry.py`、`llm/openai_compat.py`、`llm/anthropic.py`、`llm/base.py`、`repositories/sessions/sqlite.py`、`api/app.py`、`paper_retrieval/download.py` 全部存在且职责对得上）。这张表直接决定新人点不点开分篇。

### 5. "改一个功能之前，先看下面几行"（L108-L114）

> 想给模型加一个工具：处理函数写在 `src/agents/research/tools.py`。登记交给 `src/agents/common/tool_registry.py`。

这是全文**对上手最友好**的一段：把"我想改 X"映射到"去改 Y"。核对无误（`tools.py:512 build_research_tool_registry` 里逐条 `registry.register(...)`）。**必须保留，建议再补两三条**（见第六节）。

### 6. "数据落在三个地方"（L116-L120）

把对话历史（SQLite 消息表）、工作区（`data/sessions/{会话编号}/workspace/papers.json`，`WORKSPACE_SCHEMA_VERSION = 4`）、长期记忆（`src/services/paper_memory.py`，报告存成 `deep_read.json`）三处分开讲。**路径和常量逐条核对无误**。这是新人最容易搞混的地方，讲清楚了。

### 7. 全局两张 mermaid 图（L136-L163）

- 第一张分层图（前端 → 接口 → 服务 → Agent → 工具 → 数据）六个方框，一眼看懂系统形状，**必留**。
- 第二张全链路图把"主 Agent 手写循环、最多 20 轮""同轮最多 3 个工具""产物正文不落 SQLite"三个关键事实画进了图里，**必留**。

### 8. 图后的三条补充（L165-L176）

> 第二张图有一处容易看错。产物正文不放在 SQLite 里。它写在会话目录的文件里。SQLite 只登记索引，比如名称、路径、大小。

"看完图，这三件事容易看错"——这个写法要保留。后面 `MAX_TOOL_ROUNDS = 20` / `TOOL_PARALLEL_LIMIT = 3`（`src/agents/research/agent.py:54,57`，核对无误）和十二个工具名的分组列表（与 `tools.py:201-458` 的 11 个 `Tool(...)` 定义逐一对应，**数量与名称全对**）也要保留。

### 9. 七个设计决策的三段式模板（L182-L236）

**这是全文最该保留、也最容易被改坏的骨架。**

```
### 决策 N：<结论当成小标题>

**要解决的问题**：<不这么做的具体代价>
**考虑过的做法**：<被否决的方案>
**最终选择**：<当前做法>。代价是<说清代价>。
```

三条优点都要保住：

1. **标题直接给结论**（"编排方式按流程的形状选，不强行统一"、"当前工具调用用 ContextVar 存，不用普通字段"），读者扫标题就能拿走七个判断。
2. **每节结尾都写"代价是……"**（L188、L196、L204、L212、L220、L228）。不藏着代价，这是技术文档里少见的诚实写法，**一个字都不要删**。
3. **被否决的方案写明否决理由**（L218 的语义召回写了"按相似度排序几乎不触发""批量接口一次最多收 20 条，配置里却写了 32"，与删除提交 `728b908` 的提交信息逐句对得上）。这部分是面试时最抗追问的材料。

### 10. 收尾的阅读顺序（L238）

> 阅读顺序建议：先读 01，把整条链路走通。另外几篇按需深入。

一句话给出入口。**保留，但建议前移到文首**（见第六节）。

## 三、与源码不符的地方

共 8 条，按严重程度排列。

### 1. `L101` 「统一解析入口」踩了简历红线（最严重）

> 文档说：`llm_json.py  模型输出 JSON 的统一解析入口`

**源码实际**：仓库里**不是**全仓统一。

- 仍在用统一入口的：`src/agents/reading/deep_read.py:712`、`:827`（map / reduce）、`src/agents/reading/paper_qa.py:326`、`src/agents/review/analyse.py:283`、`src/utils/fulltext/figures.py:371`。
- **仍是手写解析的**：`src/agents/review/outline.py:810 def _extract_json_object()`（`outline.py:178/226/341` 调用它）、`src/agents/review/writing.py` 同样自带一份。
- **自带外层重试的**：`src/agents/review/analyse.py:112 async def _chat_json_with_retry()`。它调用 `parse_llm_json(text, fallback={})` 时**没有传** `repair` 参数（`analyse.py:283`），重试是它自己实现的。
- 顺带：`src/utils/llm_json.py:4-6` 的 docstring 自称"所有需要模型产出结构化数据的 Agent 都统一调用"，**这句话本身也与代码不符**。

**建议改成**：「`llm_json.py` 解析模型输出的 JSON。精读、问答、图片解读、综述分析共用这一份解析；大纲和逐节写作仍各自解析」。

（红线依据：不能说"全仓统一 JSON 解析入口"。可以说"精读 / 问答 / 图片解读 / 分析共用同一个 JSON 解析入口"。）

### 2. `L200` 「累加 token 用量」踩了简历红线

> 文档说：「它还要**累加** token 用量，还要往工作区写入。」

**源码实际**：工具卡上的 token 用量是**覆盖**，不是累加。

- 证据：`src/runtime/workflow.py:522`，注释原文——「只有模型回调明确提供用量时才覆盖卡片数字，普通进度更新不会把已有用量清零。」
- 卡片显示的是**最近一次上报的用量**，不是历次之和。

**建议改成**：「它还要把自己的 token 用量写到工具卡上，还要往工作区写入」。同时把 `L192` 「进度和 token 用量还要落到工具卡上」保留原样（那句没有"累加"字样，是对的）。

（红线依据：token 用量是覆盖而非累加，不能写"逐轮累加"。）

### 3. `L105` 指向的 `baseAgent.md` 不是本项目的文档

> 文档说：`src/config/            一份 LLM 适配层的设计说明（baseAgent.md）`

**源码实际**：`src/config/baseAgent.md` 是**另一个项目（nanobot）**的设计文档。

- 证据：`src/config/baseAgent.md:1` 标题为「Nanobot 多厂商大模型适配架构设计文档」；正文第 6 行起列的源码模块全是 `nanobot/providers/...`、`nanobot/config/schema.py`、`nanobot/agent/model_presets.py`。
- 证据：全文 `grep -c "Paper-Agent" src/config/baseAgent.md` 结果为 **0**，一个字都没提到本项目。
- 文档第 9 行却写着「目录按当前代码核对」，两处自相矛盾。

**建议改成**：「`src/config/` 放一份参考资料（`baseAgent.md`）。它是 nanobot 项目的多厂商大模型适配设计文档，本项目的 `src/llm` 层参考了它的设计。它不是本项目的源码，读源码请看 `src/llm/`」。或者干脆把这一行从"代码放在哪"的目录树里挪走，因为它**不是代码**。

### 4. `L34` / `L127` 说了 `research_agent`，但配置文件里没有

> 文档说：「内置档位有 `default_agent`。主 Agent 还可以选 `research_agent`。`research_agent` 没配置时自动退回 `default_agent`。」

**源码实际**：代码这一侧是对的，但配置这一侧会误导新人。

- 代码侧**对得上**：`src/agents/research/agent.py:51 RESEARCH_LLM_PROFILE = "research_agent"`；`src/services/chat_runtime.py:209-211`；回退逻辑 `src/llm/config.py:170-171`（"任何没配置或名字对不上的档位都回退到必配的 default_agent"）。
- **但 `config/model.json` 的 `agents` 键下只有 `default_agent` 和 `Read_Agent` 两项，没有 `research_agent`。** 新人照文档去配置文件里找，会找不到。

**建议改成**：「内置档位只有 `default_agent`。主 Agent 另有一个可选档位 `research_agent`，**默认配置里没有这一项**，需要自己在 `config/model.json` 里加；不加就用 `default_agent`」。

### 5. `L96-L97` 漏了会话库里的三张论文表
