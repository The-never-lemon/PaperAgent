# doc/arch/02-context-memory.md 诊断

## 一句话总评

写出了一条讲得很透的主线（每轮重建、两级收缩、只复用论文资产、思考块必须回传），但「设计理念」9 个决策整节压在开篇，新人还没看懂机制就先被灌了一轮「为什么」，而机制本身散落在 1~5 节里，读起来像先看答案再看题；另外有 4 处代码事实要改，40 处中文写作硬伤要以常用词替换。

## 一、必须保留的东西

改写时下面这些结构和讲法一条都不许丢。

- 开篇那句「模型没有记性。每次调用之前，我们都要把它需要知道的东西重新拼好。」全文的立足点在这一句，留。
- 「读完这一篇，你能回答」的 5 个问题（L7-11），是全文路线图，且与「小结」5 条一一对应，留。
- 第 0 节的 mermaid 流程图（L19-33），一张图讲完「落库 → 读回 → 修配对 → 超预算吗 → 阶段 A → 阶段 B → 发模型 → 写回」，是全篇最好的一张图，留。
- 第 0 节的三层「记忆」表格（L39-43）。四列（层 / 存什么 / 存在哪 / 谁读）一次把三层边界划清，留。
- 「设计理念」的「要解决的问题 / 考虑过的做法 / 最终选择 / 代价」四段式（L53-131）。这是全文最有价值的部分：新人最想知道的就是「为什么不用另一种做法」。整节保留，只改措辞、只调位置（见第六节）。
- 决策 7 里「建一个跨会话的聊天记忆向量库，项目已经明确否决这条路」（L113）和「摘要降级的报告故意不写进目录」（L115）。这两句是防误传的关键，留。
- 3.1 的三条件判定 mermaid 图（L289-298）加「从左边看起」的读图提示，留。
- 「以用户消息为轮边界、整轮进出」这条因果链（决策 4 + L202 + L212）：先说按消息删会切断配对，再说整轮进出所以配对天然完整。这是全文讲得最透的一段推理，留。
- 每处关键结论都附「代价是……」（L59、L83、L107、L123、L131、L246 等）。让新人看得见取舍在哪，留。
- 常量都点到了源码里的名字（`KEEP_RECENT_TURNS_LITE`、`GET_HISTORY_MAX_CHARS`、`COMPRESSED_SUMMARY_MAX_CHARS` 等），留。
- 第 4 节把「主 Agent 压聊天历史 / 子 Agent 压论文材料」两条不同策略并排对照（L346），这个对照结构留。
- 第 5 节把「思考块是协议要求」单独立节（L406），并且明确点出「历史压缩不在照顾清单里，因为它是全新的 system + user 两条消息」（L419）。这条反例很有说服力，留。
- 第 1.5 节 `get_history` 的「少量多次」设计理由（L226）和「宁可截短最老一行，也不让整段取不回来」（L224）的思路，留。

## 三、与源码不符的地方

- `L317` 文档说：「表里没有目录名时，它会去磁盘扫一遍。一旦扫到，马上把目录名写回目录表，下次不用再扫。」——这句话紧跟在 `resolve_paper_cache_dir` 的说明后面，读者会以为 `resolve_paper_cache_dir` 会扫盘。
  源码实际：`resolve_paper_cache_dir`（`src/services/paper_memory.py:191`）只做两件事：查目录表里记下的目录名，查不到就按当前编号拼一个路径返回，全程不遍历磁盘。真正扫盘的是 `_locate_cache_dir_on_disk`（`src/services/paper_memory.py:760`），把目录名写回目录表的是 `_remember_located_cache`（`src/services/paper_memory.py:800`），由精读写回那条路径（`record_fulltext_deep_read`，`src/services/paper_memory.py:220`）调用。
  建议改成：「表里没有目录名时，精读完成后的 `_locate_cache_dir_on_disk` 会去磁盘扫一遍。一旦扫到，`_remember_located_cache` 马上把目录名写回目录表，下次不用再扫。」

- `L308` 文档说：「其中 `paper_key` 是主编号，写法带 `doi:` 或 `arxiv:` 前缀。」
  源码实际：`paper_key`（`src/paper_retrieval/identity.py:36`）在前两条都拿不到时，会退回整理过的标题键，写成 `title:...`（`_title_key`，`src/paper_retrieval/identity.py`）。也就是说 `paper_key` 有三种写法，不只两种。
  建议改成：「其中 `paper_key` 是主编号。有 DOI 就写 `doi:` 前缀，arXiv 论文写 `arxiv:` 前缀；两者都没有时退回标题键，写 `title:` 前缀。」

- `L390` 文档说：「这类失败报出来的错永远是「没有返回可解析的 JSON」，真实原因藏在后面。」
  源码实际：`analyse.py` 已经把这类失败做了细分。`_describe_unparsable`（`src/agents/review/analyse.py:287`）会给出三种说法：「模型在达到输出上限…时停止，没有写出完整的 JSON」「模型只输出了思考过程，没有输出任何正文内容」「模型没有返回可解析的 JSON」，并由 `_parse_response`（`src/agents/review/analyse.py:271`）写进 `reason`。文档自己的 `L397` 也写了「不再笼统报一句「不可解析」」，两处直接打架。
  建议把 L390 改成：「这类失败最常见的一句话是「模型没有返回可解析的 JSON」。真实原因要靠下面这几种细分说法才能看出来。」

- `L251` 文档说：「最近 5 条检索历史，形如「- 「主题」（HH:MM）→ 命中 N / 新增 M」」。
  源码实际：每行打印的是 `entry.concept_groups_summary or entry.topic`（`src/agents/research/agent.py:981`），也就是优先显示概念组摘要，摘要为空才退回主题；时间戳取 `entry.timestamp[11:16]`，是 UTC 时间。
  建议改成：「最近 5 条检索历史，形如「- 「概念组摘要」（HH:MM）→ 命中 N / 新增 M」；概念组摘要为空时显示检索主题。这里的 HH:MM 是 UTC 时间。」

已核对无误、不要改的地方（改写时可放心引用）：两处行号引用 `src/agents/research/agent.py:702`、`src/agents/research/agent.py:577`，代码围栏 `90:98:src/agents/common/context_budget.py`，以及 `context_budget.py:28`、`context_budget.py:24`、`src/llm/config.py:45`、`src/services/session_runs.py:215`、`src/agents/research/tools.py:177`、`src/models/workspace.py:489` 全部对得上。各常量值也全部对得上：`KEEP_RECENT_TURNS_LITE=6`、`COMPRESS_INPUT_MAX_CHARS=16000`、`COMPRESSED_SUMMARY_MAX_CHARS=400` 与温度 0 / max_tokens 800、`GET_HISTORY_MAX_CHARS=3000` 与 2984、`CHUNKER_VERSION=10`、`max_atomic_characters=4000`、`max_chunk_characters=1200`、`DEEP_READ_MAP_CONCURRENCY=3`、`MAP_NOTE_MAX_CHARS=500`、`REDUCE_INPUT_MAX_CHARS=150000`、`REDUCE_FIGURE_NOTES_MAX_CHARS=6000`、`REPORT_SUMMARY_CHARS=1500`、`TOOL_RESULT_MAX_CHARS=20000`、`QA_READ_MAX_CHUNKS=6`、`QA_READ_CHUNK_MAX_CHARS=1200`、`QA_TOC_MAX_ENTRIES=60`、`QA_TOC_PREVIEW_CHARS=60`、`QA_MAX_TOOL_ROUNDS=4`、`QA_CONTEXT_MAX_CHARS=30000`、`ANALYSE_MAX_ATTEMPTS=3`、`ANALYSE_MAX_TOKENS_CEILING=32768`。占位符文案、降级说明文案、`……[旧回复已截断]`、`……[已截断]`、`LLM_FAILURE_MESSAGE` 文案均为逐字引用，正确。三张表格、四张 mermaid 图的流程也和代码一致。

## 五、对新人上手不友好的地方

- `L51` 说「每个决策说清三件事」，后面却列了四项（要解决什么问题、考虑过哪些做法、最后选了什么、代价是什么）。新人会停下来数一遍，先改成「四个问题」。
- 第 0 节的图和第 1 节正文对不上号：图上标的是「阶段 A 归档 / 阶段 B 压缩」，1 节却从「system 由三块拼成」讲起。建议在 1 节开头补一句「第 0 节那张图里，`system` 就是最后拼出来的那一条消息」。
- `L210` 「格式是「序号. 行」」没头没尾。新人看不出「序号. 行」长什么样，必须给一个真实例子，例如「1. 用户想查联邦学习的隐私保护方案」。
- `L308-311` 一句话塞了六种键：`doi:`、`arxiv:`、裸 paperId、缓存目录名、`title:`、工作区 paperId，却没有先给一句总述。建议开头补「同一篇论文的所有写法都挂在同一条目录记录上」，再逐个举例。
- `L313-319` 那条「历史教训」讲目录名早期跟着 paperId 起、后来编号变了。新人不知道「编号变了」指什么。建议补一句「换数据源后，同一篇论文会拿到一个新的 paperId」。
- `L176` 突然插入「`src/agents/research/agent.py` 里另有一份同名定义，全仓没有引用它」。这是给改代码的人看的提醒，对「从没接触过项目的人」是噪音，建议移到脚注或删掉。
- `L261` 「召回精读报告也刻意放进同一把锁里。它要往工作区写报告」——「它」指代不清（指召回这件事，还是指报告？）。建议改成「召回时也要往工作区写报告，所以同样在这把锁里做」。
- `L302` 「写入在 `record_fulltext_deep_read` 里判断」，「写入」指什么没交代（写进论文目录表）。
- `L376` 「旧做法一次性放进全文，中段一截」没说清是谁截的、截成什么样。建议改成「旧做法把全文塞进提示词，超过上限就从中间截断」。
- `L390` 与 `L397` 的说法互相矛盾（一句说「永远是那句笼统报错」，一句说「不再笼统报」）。新人读到这里不知道该信哪一句，必须改到一致。
- `L348` 「map-reduce」第一次出现就直接用了英文，没给中文解释。
- `L419` 「终答纠偏」第一次出现没解释（指终答里引用了工作区不存在的论文编号时，注入一条指令让模型重写）。

## 六、结构建议

- **「设计理念」整节后移，或拆开贴回各节。** 现在的顺序是「0 全局 → 设计理念（9 个决策）→ 1 对话历史 → 2 工作区 → 3 长期记忆 → 4 子 Agent 材料 → 5 思考块」。新人还没搞懂「消息怎么拼」，就先被 9 个决策灌了一遍「为什么」，这是本篇最大的上手障碍。两种改法任选其一：（a）把整节挪到第 1 节之后，读者带着「原来是这样」再看决策；（b）拆开——决策 1~6 归第 1 节（对话历史），决策 7~8 归第 3 节（长期记忆），决策 9 归第 5 节（思考块），各贴在对应小节的开头或末尾。推荐 (b)，每节都能「先讲现象、再讲取舍」，最顺。
- **第 3 节拆成四小节。** 现在的 3.3 一节里混了四件事：写入时机、召回时机、`recalled` 字段写在哪、迁移与启动注入。建议拆成：3.1 什么算「可召回」、3.2 身份怎么认、3.3 什么时候写入、什么时候召回（含 `recalled` 字段）、3.4 迁移与启动（把 L332-342 整段挪进这里）。现在这段内容挂在一个「什么时候写入、什么时候召回」的标题下，读者找不到。
- **第 2 节标题改掉。** 标题是「工作区：本会话的调研状态机」（L230），但正文讲的是三态、落盘原子性、加锁、软删除，没有一处是「状态机」。建议改成「工作区：本会话的论文状态」。
- **第 4 节里「综述分析」那两块内容挪走。** L388-397 大段讲分析失败的分类重试（`_attempt_max_tokens` / `_attempt_messages`），这是可用性问题，不是「材料上下文」问题。建议挪到 [可用性保证](04-availability.md)。第 4 节只留「精读怎么分块」「追问怎么按需取原文」「写作怎么按需取片段」这三条真正的材料策略。
- **第 5 节和第 1 节有重复。** 思考块在决策 9（L127-131）、1.3（L197）、第 5 节（L408-421）各讲了一遍。建议第 5 节只留「协议要求 + 四条照顾链路清单 + 压缩不在清单里这条反例」，把「阶段 A 会清空思考块」这类机制细节留给 1.3，避免新人读到第三次才发现是同一件事。
- **第 0 节和后面几节之间补一句桥。** 建议在第 0 节表格后加一句：「后面每一节对应图上的一段：第 1 节是中间那两条处理线，第 2、3 节是工作区和本机资产，第 4、5 节是主 Agent 之外的上下文。」
- **小结加一张对照表。** 现在的小结 5 条和开篇 5 问对应得很好，建议在小结后面补一张「想改哪儿 → 去看哪个文件」的表（拼消息 → `build_llm_messages`；预算 → `context_budget.py`；压缩 → `_compress_completed_turns`；工作区 → `models/workspace.py`；长期记忆 → `services/paper_memory.py`；思考块 → `llm/base.py` 的 `attach_reasoning`）。新人上手第一步是找文件，这张表比正文更管用。

## 七、简历红线核对（本篇）

本篇没有触碰任何一条红线：没有出现「全流程基于 LangGraph 编排」「全系统断点续跑」「统一 JSON 解析入口」「熔断器」「服务端背压」；L390-397 讲的 `analyse.py` 重试是真实存在的 `_attempt_max_tokens` / `_attempt_messages`，不是笼统的「超时自动重试」；L45 和 L113 明确写了「没有跨会话的聊天记忆向量库」「向量库这条路已被否决」，和红线一致；「字符率回填」讲的是回填比例，不是 token 累加。改写时保持这些表述不变即可。

最后一句总结：这篇文档最大的问题是**结构顺序反了**——它把「为什么这么设计」放在「怎么设计的」前面，让一个从没接触过项目的人先看 9 段取舍论证、再去 1~5 节里自己拼凑机制；只要把设计理念拆回各节、修掉「扫盘该记在哪个函数名下」等 4 处代码事实，剩下的就是替换 19 个比喻性动词和 8 处英文术语标注的收尾工作。
