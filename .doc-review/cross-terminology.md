## 2. 同一件事，不同篇叫法不同（同物异名）

逐条给现象、出处和统一建议。

### 2.1 工具卡 / 卡片

- ①L25 定义「工具卡」，①W 全文用它。
- ④几乎只用「卡片」，13 次里只有 1 次写「工具卡」（④L504）。例如④L116「界面上三张卡片的内容会互相串」。
- ⑤混用：⑤L205「失败卡」，⑤L265「每张工具卡可以带真实的 `input_tokens`」。

**建议**：统一叫「工具卡」。首次出现处可以补一句「工具卡就是界面上代表一次工具调用的那张卡片」，之后不再单用「卡片」。

**理由**：界面上的卡不止一种。单用「卡片」会和「卡片消息」（见下条）撞车。

### 2.2 对话卡 / 卡片消息 / 系统卡片

- ①L26 定义「对话卡」，指代表主 Agent 这一轮回复的那张卡。
- ④L373、④L515 把同一类东西叫「卡片消息」，指 `role="system"`、`metadata.kind="paper_list"` 的消息。
- ②L709 又叫「系统卡片」：「`message` 用来推系统卡片，比如精读完成卡片」。
- ④L402 反过来用回了「对话卡」。

这里其实有两种东西。一种是进度卡片，由 SSE 事件画出来。另一种是消息卡片，走消息表，`role` 是 `system` 或 `assistant`。文档现在用三个词混着说。

**建议**：

1. 进度卡片一律叫「工具卡」。
2. 消息卡片一律叫「卡片消息」，在①的词汇表补一行。
3. 删掉「系统卡片」这个叫法，②L709 改成「卡片消息」。

**理由**：两种卡片的产生路径完全不同。一个是事件，一个是消息。混着叫，读者会以为刷新页面能重放工具卡。

### 2.3 摘要精读 / 摘要降级 / 降级成摘要 / 摘要报告

同一个动作有五个叫法：

- ②L219、②L521「摘要精读」；
- ①L220、②L522、③L115、⑤L307「摘要降级」；
- ④L372「精读降级成摘要」、④L523「降级成摘要」；
- ②L237「摘要报告」；
- 代码常量 `source=abstract_fallback`。

**建议**：正文统一用「摘要精读」。首次出现写成「摘要精读（`source=abstract_fallback`，拿不到全文时用摘要代替全文做一次精读）」。形容词性用法一律写「摘要精读的」。

**理由**：「摘要报告」这个叫法最危险。它和「精读报告」只差两个字，容易让读者以为两者结构不同。实际两者结构相同，只有 `source` 和 `notice` 不同。

### 2.4 阶段 A 归档 / 零成本剥离 / 预算收缩 / 两级收缩

- ①L222 决策 6 标题「零成本收缩」，①L50「两级收缩」。
- ③L192 小节标题「阶段 A：零成本剥离（不调模型）」。
- ③L137「配对修复和预算收缩两道处理」。
- ③L69 决策 3 标题「超预算先做零成本归档」，③L196 占位符文案「[历史工具结果已归档……]」。

**建议**：统一为「阶段 A 归档」「阶段 B 压缩」。动作词只留「归档」和「压缩」。①L222 的「收缩」改成「归档」。

**理由**：现在「收缩」既指整个两级机制（①L50），又指阶段 A 的动作（③L137），范围不清。

### 2.5 会话库 / 业务库

- ③L43、③L336「会话库」。
- ②L655「业务库 `data/session_store.db`」。
- ①L159「SQLite 会话库」。

**建议**：统一叫「会话库」。②L655 改成「也不用和会话库 `data/session_store.db` 抢同一把写锁」。

**理由**：「业务库」让人猜不到它就是存会话的那个库。

### 2.6 进度上报器 / reporter / `WorkflowNodeReporter`

- ②L107、②L115「进度上报器」。
- ④L394 代码示例里叫 `reporter`。
- ②L705「`WorkflowNodeReporter`（节点用它把进度发给前端的对象）」。

**建议**：正文统一写「进度上报器（`WorkflowNodeReporter`）」。代码示例保留变量名。

### 2.7 事件总线 / 事件扇出 / broker

- ①L151 mermaid 图里写「内存事件总线」。
- ⑤L232 写「`SessionRunBroker` 在进程内存里做事件扇出」。
- ⑤L232、⑤L240 又简称「broker」。

**建议**：正文统一写「事件总线（`SessionRunBroker`）」。「扇出」这个说法只在解释原理时用一次。

### 2.8 继续运行 / 续跑 / 恢复

- ②L133、②L139「继续运行」。
- ④L530、⑤L207「续跑」。
- ②L41、②L145「恢复入口」。

**建议**：统一为「继续运行（resume）」。首次出现处写清楚它是「从检查点接着做」。

### 2.9 回灌 / 回填 / 回流 / 写回

同一个「把结果送回上游」的动作，四个词混用：

- ④L32「回灌结果」；
- ③L368「精读报告的摘要回灌」；
- ④L255「回填 `role=tool`」；
- ④L402「不会混进对话卡」（上文是「子 Agent 回流的内容」）；
- ③L190「重建历史时再写回消息对象」。

**建议**：按对象分开，只留两个词。

1. 「回填」：把工具结果写回消息列表。
2. 「回流」：子 Agent 的产出返回主 Agent。

「回灌」「写回」不再使用。

**理由**：三个词都表示「写回去」，但写回的层不同。分开后，改代码时不容易搞错位置。

### 2.10 上游 / 网关 / Provider / 模型服务

- 「Provider」：适配层的对象（①L35、⑥L26）。
- 「上游」：远端的模型接口（③L63、④L116）。
- 「兼容网关」：第三方的兼容实现（④L116、⑥L68）。
- 「模型服务」：只出现在用户可见的报错文案里（③L410、⑤L168）。

**建议**：保留现在的分工。在①的词汇表补一行「上游 / 兼容网关」，写明前者指远端接口，后者指第三方兼容实现。「模型服务」只用于引用报错文案。

**理由**：分工已经存在，只是没有写下来。写下来后，读者才知道「网关返回 3600 秒」（⑤L167）说的是哪一层。

### 2.11 主循环 / 主 Agent 循环 / 多轮工具循环

- ②L41「主 Agent 的多轮工具循环」；
- ④L268「主循环最多 20 轮」；

**建议**：统一为「主循环」。首次出现写「主循环（主 Agent 手写的多轮工具循环）」。

### 2.12 工具轮次 / 轮次

## 3. 同一个词，不同篇意思不同（同名异义）

这一类最危险。逐条列出。

### 3.1 快照 —— 违反了本套文档自己的约定（最严重）

- ①L44 专门澄清：「「快照」在本套文档里指模型配置快照（`ProviderSnapshot`），和检查点是两回事。」
- ③L265 却写：「`SessionWorkspace.remove_papers`（`src/models/workspace.py:489`）把整篇快照挪进 `removed_papers`。」

③L265 的「快照」指的是论文条目的一份记录副本。这和 `ProviderSnapshot` 毫无关系。

**危害**：①刚立了约定，③就破了。读者读到③L265 会以为删除论文和模型配置有关。

**建议**：③L265 改成「把整篇论文记录挪进 `removed_papers`」。同时检查「快照」在③里是否还有别的用法（本次只有这一处）。

### 3.2 摘要 —— 四种含义

| 含义 | 出处 | 举例 |
| --- | --- | --- |
| 论文摘要 | ③L386「原文摘要」 | 论文自己的 abstract |
| 结构化摘要 | ③L386、③L403、②L689 | `get_extraction` 取出的整理结果 |
| 对话摘要 | ③L210「此前对话摘要」、③L85「压缩摘要」 | 阶段 B 压出来的要点 |
| 摘要精读 | ②L219、④L309 | 拿不到全文时的降级精读 |

**危害**：③L386 一行里同时出现「原文摘要」和「结构化摘要」。读者要读到「原文」两个字，才知道第一个是论文自己的摘要。③L91「摘要只进模块级缓存」的「摘要」指的是对话摘要，但字面上也可以读成论文摘要。

**建议**：

1. 论文自己的摘要固定写「摘要」或「原文摘要」。
2. 派生结果固定写「结构化摘要」。
3. 压缩结果固定写「对话摘要」，不要单用「摘要」。
4. 降级精读固定写「摘要精读」。

### 3.3 记忆 —— 三种含义

- 「长期记忆」：本机论文资产（①L30、③第 3 节）。
- 「记忆」当作对话历史：④L220 的工具表把 `get_history` 的类型写成「记忆」。
- 「记忆」当作三层统称：②L213 决策 5 标题「记忆分三层」，②L216「记忆分三层」的内容是对话历史、工作区、长期记忆。

**危害**：④L220 的分类名和①②③的「长期记忆」是相反的意思。④L373「入工作区加记忆召回」的「记忆」又指长期记忆。同一篇④里，L220 和 L373 的「记忆」指两个东西。

**建议**：

1. ④L220 的分类名改成「对话历史」或「历史回取」。
2. 统称一律写全「三层记忆（对话历史 / 工作区 / 长期记忆）」。

### 3.4 摘要阅读 / 摘要精读 —— 只差一字，指两件事

- 「摘要阅读」：`ReadAgent` 只看摘要就判断相关性（①L70、②L497）。用在 `evaluate_papers`。
- 「摘要精读」：拿不到全文时，用摘要代替全文走一遍精读流程（②L219）。

**危害**：两个词都是「摘要 + 阅读」，读者很容易当成一件事。实际一个是评价工具，一个是降级路径。

**建议**：把「摘要阅读」改成「相关性评阅」，或写全「基于摘要的相关性评阅」。②L497 和①L70 同步改。

### 3.5 归档 —— 两件不相干的事

- 历史归档：阶段 A 把旧工具结果换成占位符（①L222、③L69、③L196）。
- 论文归档：`remove_papers` 做软删除，把论文挪进 `removed_papers`（③L265、④L215「移除的论文进归档，可以恢复」）。

**危害**：③L196 的占位符文案是「[历史工具结果已归档……]」。③L265 讲的是论文软删除。同一篇里两个「归档」指不同的表和不同的恢复方式。

**建议**：论文那一处改成「回收站」或「论文归档区」。占位符文案不动（它是源码原文）。

### 3.6 块 —— 有时指正文块，有时指片段

- 正文块：标题、段落、公式、表格、图（②L562、③L352）。这是切分的输入单位。
- 片段：③L287「片段没有切坏的超长块（`chunks_are_usable`）」，判据是每个片段不超过 4000 字。

**危害**：③L287 的「超长块」其实指一个太长的片段。而②L562 的「块」是切分前的正文单位。两个「块」在切分流程里前后相邻，读者极易搞反。

**建议**：③L287 改成「片段里没有超长的那些（`chunks_are_usable`）」。全文的「块」只保留「正文块」一个意思。

另外「段」也混用：②L567「装到 1200 字就换下一段」的「段」指片段，而「段落」指正文块。建议「段」不再单用，一律写「片段」。

### 3.7 轮 —— 工具轮和用户轮

- 工具轮：模型调用一次加执行一批工具（②L353「同轮最多 3 个工具并行」）。
- 用户轮：一条用户消息带它引发的全部工具轮（③L194「从最老的用户轮开始处理，最近 6 轮不碰」）。

**危害**：③同一篇里两种都在用。③L105「上一轮实测已吃满窗口 75%」指的是上一次模型调用，也就是工具轮。③L212「最近 6 轮是下限」指的是用户轮。读者按前者去数，会把「6 轮」数成 6 次模型调用。

**建议**：

1. 单用「轮」一律指工具轮。
2. 指用户轮时必须写全「用户轮」。
3. ③L105 改成「上一次调用」。

### 3.8 卡片 —— 事件画的卡和消息画的卡

见第 2.2 条。④L116 的「三张卡片」是工具卡，④L515 的「卡片消息」是走消息表的。两者刷新页面的表现完全不同。

**建议**：按第 2.2 条统一。

### 3.9 配置 —— 四种范围

- 档位（⑥L26）：一组模型配置。
- 连接配置 `ProviderConfig`（⑥L277）：地址、密钥、超时。
- 系统配置 `SystemConfig`（⑥L406）：三段，含检索和阅读。
- 模型配置快照（②L117）：装配后的结果。

**建议**：这四个都不单独写「配置」。一律带限定词写全。②L612「模型配置快照」已经写全，是正面例子。

### 3.10 阶段 —— 三种范围

- 综述图的节点阶段 / 阶段边界（②L161、⑤L220）。
- 上下文收缩的阶段 A / 阶段 B（③L192）。
- 实施阶段（④L196 的一段源码 docstring：「按当前实施阶段构建主 Agent 可用的工具注册表」）。

**建议**：③的两处写全「收缩阶段 A / B」。④L196 属引文，不动。

### 3.11 事件 —— 和「卡片消息」的界线

- ①L37 定义「事件」是后端通过 SSE 发往前端的一条消息。
- ④L515 又把「`role="system"` 的消息」叫「卡片消息」，⑤L234 说 `delta` 和 `reasoning_delta` 不落库。
- 于是「事件」和「消息」的关系始终没说清：卡片消息算不算事件？它落不落事件表？

**建议**：在①的词汇表补一行「卡片消息」，并说明它和「事件」各走哪张表。在⑤第 4.2 节补一句「卡片消息走消息表，进度走事件表」。

### 3.12 取消 / 停止 / 中断 —— 三种状态没并列说明

- 用户点停止 → run 标 `cancelled`（⑤L204）。
- 进程被强杀 → 启动清理改成「已中断」（⑤L133）。
- 工具没跑完 → 工具结果标 `interrupted`（④L486）。

**危害**：三个词都表示「没跑完」，但它们是三种状态，收场方式不同。②L158「被中断」指第三种，⑤L133「已中断」指第二种，⑤L204「cancelled」指第一种。

**建议**：在⑤补一张三行的小表，写清触发原因、状态值、恢复方式。

### 3.13 引用 / 引文

- 「引用」：正文里的 `[paper_id]` 编号（②L425）。
- 「引文」：引用关系图，`expand_by_citations` 用它（④L384「引文扩展走 `async_related`」）。

当前没有混用，但两词只差一字，且都出现在论文语境里。

**建议**：在①的词汇表各加一行。或者把「引文扩展」改成「引用关系扩展」。

## 6. 附带发现：三处可能踩到简历红线

这一节不属于术语问题，但后果比术语问题重，所以单列。

### 6.1 ①L101 把 `llm_json.py` 说成「模型输出 JSON 的统一解析入口」

原文（①的目录树）：

```text
  llm_json.py            模型输出 JSON 的统一解析入口
```

事实是：`analyse.py` 虽然用了 `parse_llm_json`，但它自带一层外层重试；`outline.py` 和 `writing.py` 仍是手写解析。

**建议**：改成「JSON 解析的公共函数」或「供部分环节调用的 JSON 解析工具」。

**理由**：红线要求不能说「全仓统一 JSON 解析入口」。现在的写法正好命中。

### 6.2 「累加 token 用量」和「用量只在显式传入时覆盖」互相矛盾

- ①L200「它还要累加 token 用量」；
- ②L200 同句；
- ⑤L265「子 Agent 的用量累加到所属工具卡」；
- ④L120「用量和进度就记到别人头上」；
- ②L718 又说「用量只在显式传入时覆盖……普通进度更新不会把已有用量清零」。

红线的口径是「token 用量是覆盖而非累加」。①②⑤的「累加」措辞和它冲突。

**建议**：改成分层说清。「卡片上的用量按最近一次上报覆盖」；如果确实要说明多次调用会合计，就写「合计」而不要写「累加」。

**理由**：「累加」是最容易被追问的措辞。

### 6.3 ④L308 的引文含「优雅降级」，但④的正文没有解释

这一处本身合规（逐字引用源码不受用词约束，①L43 已经声明）。但④是读者第一次见到「优雅降级」的地方，而解释在⑤。

**建议**：④L308 下方的说明里补半句「优雅降级的含义见可用性保证的决策 5」。
