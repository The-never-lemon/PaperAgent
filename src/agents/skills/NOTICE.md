# 技能文档的来源与许可

`src/agents/skills/` 下的这些 markdown 文档是给模型看的方法论说明，会被拼进
`src/agents/Prompts.py` 里对应的系统提示词。它们不是程序代码，但会随分发包一起
分发，所以来源和许可要写清楚。

## 一、`paper-deep-reading.md`

**来源**：`https://github.com/huangkiki/dailypaper-skills`（Apache License 2.0）。

具体取自下面两个文件里「怎么判断、怎么评价」这一部分内容：

- `skills/daily-papers-review/SKILL.md` 的「铁律：基于事实评价」一节（四条「绝对禁止」
  与其对称的「你可以（且应该）做的」清单）
- `skills/paper-reader/SKILL.md` 的质量规则，以及
  `skills/paper-reader/references/quality-standards.md` 里关于表格与公式的提取要求，
  以及同一文件「公式质量检查」一节的差错类型（符号约定不一致、公式与文字描述不一致、
  漏掉关键算子等）

**做了哪些改动**：

1. 改写成中文条目式表述，并压到很短的篇幅（每个小节都有字数上限，见下）。
2. **只保留方法，去掉全部执行步骤**——原文里的 Obsidian 笔记保存、Zotero 集成、
   `[[概念]]` 双链、图片下载与 URL 去重、概念库维护、git 提交等，在本项目里没有
   对应的执行环境，全部删除。
3. **去掉了原文的「毒舌」语气与 emoji 判决标签**：本项目产出的是给用户存档和追问
   用的评分报告，语气要求会污染评分理由字段。
4. 「零遗漏所有 Figure / 公式 / Table」这条**没有采用**：精读报告的结构是固定的，
   里面没有承载图像、表格、公式的字段，所以「全部出现」这件事没有地方落。原文中
   关于「装不下时先保什么」的取舍思路被保留下来，改写成「逐段阅读取舍」——
   那一节讲的正是分段阅读时的优先级，与报告字段无关，因此不受此限制影响。
5. 把原文中面向「笔记」的说法统一改成「输入材料」，因为同一份内容要同时用于
   「有分段笔记的汇总」和「只有标题摘要的降级」两条路径。
6. 「公式写法」分成了排布与内容两层。排布层（`$...$` / `$$...$$`）是本项目自己的
   要求，因为前端按这个渲染公式；内容层的四条（符号沿用原文、算子写全、文字描述的
   性质要体现在公式里、公式残缺时如实说明）来自上面提到的 `quality-standards.md`。
7. 「逐段阅读取舍」里「超出部分从末尾截掉、最该留的写在前面」这几句**不是上游内容**，
   是本项目按 `deepReadAgent.py` 的实际实现补的：分段笔记在模型输出之后由程序按字数
   从尾部硬切到 500 字，模型看不到截断位置，所以必须要求它把重要的内容排在前面。
   原有的「先保方法与实验数据」是同一个意思的上游说法，一并保留。

**依据**：Apache License 2.0 第 4 条要求随分发附上许可证副本。副本见同目录下的
`LICENSE-APACHE-2.0.txt`。

## 二、`literature-review.md`

**来源**：整理自一份本地收集的、标题为「文献综述写作」的中文材料（文件名为
`SKILL.md`）。**该材料没有附带任何许可证，正文里也没有版权声明**，无法确认其来源
与授权，因此**没有复制它的任何文字**。

文档里实际使用的内容——按时间 / 主题 / 方法流派 / 理论四种组织逻辑，以及
「主题句 → 文献支持 → 综合分析 → 批判性评价 → 过渡」这段段落骨架——是学术写作里
通行的通用方法，任何一本写作指南都会讲到，不构成对某一份文档的复制。

**没有采用的部分**：该材料里关于文献检索策略、常用数据库清单、文献管理软件
（Zotero / EndNote / Mendeley）的内容，以及引言与结论的写作模板——前两类在本项目
里由检索工具自动完成，第三类与综述流水线「只产出正文章节」的设计相冲突。

**本次补充的判据**（不在上述任何来源里，是本项目自行拟定的表述，供模型自检用）：

- 「正文写作原则与段落骨架」里判断逐篇罗列的判据（同一段里连续两句以上以论文名或
  `[paperId]` 作主语），以及素材只够一篇、证据为空时的降级写法。
- 「正文审查清单」里「有没有用形容词代替证据」这一条。加它是因为正文审查节点只拿得到
  小节任务和正文草稿，看不到证据，原先那条「有没有批判性评价」在审查时根本无从判断。
  批判性评估的要求随之挪进了「正文写作原则与段落骨架」，写手拿得到证据，那里才做得成。
- 「章节组织结构」里的两条自检办法（把标题连起来能不能一句话说出组织线索；一半以上的
  章按同一逻辑拆）。

## 三、篇幅上限（维护时注意）

这些文档会被追加到已有的系统提示词末尾，直接增加每一次模型调用的输入长度。所以
每个小节都有硬性上限，改文档时不要超：

| 文档 / 小节 | 上限 | 现有 | 说明 |
|---|---|---|---|
| `literature-review.md` / 章节组织结构 | 320 汉字 | 308 | 注入大纲阶段的提示词 |
| `literature-review.md` / 正文写作原则与段落骨架 | 380 汉字 | 375 | 注入逐节写作的提示词 |
| `literature-review.md` / 正文审查清单 | 200 汉字 | 149 | 注入正文审查的提示词 |
| `paper-deep-reading.md` / 逐段阅读取舍 | 210 汉字 | 198 | 注入分段阅读的提示词，**按块调用多次，乘数最大**，所以额度卡得最紧 |
| `paper-deep-reading.md` / 公式写法 | 230 汉字 | 224 | 注入汇总与降级两条路径。排布那段不是来自上游素材，是本项目加的：前端的精读报告按 `$...$` 渲染公式（见 `front/src/components/chat/MathText.vue`），模型不按这个写法输出就渲染不出来 |
| `paper-deep-reading.md` / 评价纪律 | 480 汉字 | 466 | 注入汇总与降级两条路径的提示词 |

「现有」一列是 2026-09-13 这一版的实际汉字数，改完顺手更新它，便于下一次修改时知道还剩多少余量。

**这些上限是人工约定，程序并不检查**（程序只检查下面那条 `JSON`）。超了不会报错，只会
静默拉长每一次模型调用的输入，所以只能靠改的人自己守。

另外，「逐段阅读取舍」这一节**不得出现 `JSON` 字样**：分段阅读输出的是纯文本笔记，
和汇总阶段的 JSON 输出要能区分开。程序启动时会检查这一条，违反了会直接报错。
